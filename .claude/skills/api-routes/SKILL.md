### Backend API Routes

**Auth (no JWT)**
- `POST /api/auth/register` — self-service business signup (`EmailVerified = false`); auto-creates Mon–Fri 09:00–18:00 working hours for an `Appointment`/`Both`-model business; sends a 6-digit email verification code (`devCode` in the response body in Development, matching `DevEmailSender`'s no-op-in-dev pattern)
- `POST /api/auth/login` — `{ email, password }` where the `email` field's value is matched against either the business's real email **or** its system-generated `Username` (field name kept as `email` for compatibility — see [Business owner onboarding](#business-owner-onboarding-self-service--admin-approved)); returns JWT token (30 days, carries a `mustChangePassword` claim); **403 `{ emailNotVerified: true }`** if not yet verified (frontend responds by requesting a fresh code and dropping into the verify-code view)
- `POST /api/auth/verify-email` — `{ email, code }`; marks the business verified and returns a JWT (`LoginResponse`), logging them in directly
- `POST /api/auth/resend-verification` — `{ email }`; 45s cooldown + 5/hour cap
- `POST /api/auth/forgot-password` — `{ email }`; sends a 6-digit reset code (`devCode` in Development), same cooldown/cap as email verification. Always 200, even for an unknown or disabled email (sends nothing), so it can't reveal which emails have accounts
- `POST /api/auth/reset-password` — `{ email, code, newPassword }`; verifies the code, updates the password, and returns a JWT (`LoginResponse`), logging them in directly. An unknown email gets the same 400 as a wrong code. Ends every other login (see Session rules)
- `PATCH /api/auth/change-password` (`BusinessOnly`, `[AllowWithPendingPasswordChange]`) — `{ currentPassword, newPassword }`; a wrong `currentPassword` is 400 `{ currentPasswordIncorrect: true }`, throttled like login (`LoginThrottle` scope `change-password`); a `newPassword` equal to the current one is 400 `{ samePassword: true }`, so a temp password can't just be kept. `/admin/set-password` also has a Sign out link. The only `BusinessOnly` action reachable while `MustChangePassword` is set (an admin-issued temp password) — clears the flag and returns a fresh token without the `mustChangePassword` claim

**Admin (JWT required — business ID read from token claims, never from body, `BusinessOnly` policy)**
- `GET/PATCH /api/admin/settings` — business profile, language, booking limits, and discovery fields (`city`, `addressLine`, `mapUrl` free text; `isListed` directory toggle — `mapUrl` must start `http(s)://`). `AdminController.SettingsInputError` answers 400 (nothing saved) for a booking limit outside 1–1000, a `language`/`chatbotDefaultLanguage` other than exactly `EN`/`AR`/`HE`, a chatbot message over 1000 characters, or an inquiry/cancel-approval phone (`PhoneNormalizer.IsValid`) or email (`EmailAddress.IsValid`) that can't work; those phones are stored in E.164 and whitespace-only chatbot messages are stored as null (built-in default). WhatsApp number is read-only here — see [WhatsApp chatbot: self-hosted via Baileys](#whatsapp-chatbot-self-hosted-via-baileys-whatsapp-bridge)
- `GET /api/admin/reviews` — this business's reviews (incl. hidden), newest first, with reviewer name + linked item name
- `POST/DELETE /api/admin/reviews/{id}/reply` — set / clear the owner's public reply
- `GET /api/admin/chats`, `GET .../chats/unread-count`, `GET .../chats/messages?phone=`, `POST .../chats/read` `{ phone }`, `POST .../chats/messages` `{ phone, text }`, `POST .../chats/booking-link` `{ phone, itemId }`, `POST .../chats/finish` `{ phone, sendServiceList }` (`ChatsController`) — the owner's Chats page, see [Owner Chats page](#owner-chats-page)
- (`/api/admin/chatbot-inquiries` removed 2026-10-30: the owner reads and answers Inquiry-mode messages on `/admin/chats`.)
- `GET/POST /api/admin/items` — items CRUD (includes `photoMode` + `galleryPhotos`)
- `PATCH/DELETE /api/admin/items/{id}` — update / soft-delete (IsActive = false)
- `POST /api/admin/items/{id}/gallery` — upload a gallery reference photo (JPG/PNG/WEBP, 5MB max)
- `DELETE /api/admin/items/{id}/gallery/{photoId}` — remove a gallery photo
- `GET/POST /api/admin/schedule` — working hours (upsert by DayOfWeek). `SchedulePage.tsx`'s Working Hours section is **read-only** (day name, next calendar date, hours or "Closed" per row) — it's a mirror of whatever's currently live, not an editor, except that a row whose date falls inside the pending/active `PresetSchedule` range shows that preset's hours for the day (with a preset-name badge), and a row after an already-running range's `EndDate` shows the Default preset's hours it will revert to (`hoursForRow`); the owner edits hours only through the Default schedule preset (below). The endpoint itself is unchanged and still callable directly (used internally by `SchedulePresetService.UpsertWorkingHours`).
- `POST/DELETE /api/admin/schedule/breaks/{id}` — recurring breaks. The endpoints are unchanged, but `SchedulePage.tsx`'s Recurring Breaks section is now **read-only** (same treatment as Working Hours, added 2026-09-21) — breaks are edited per-preset in `PresetEditorModal.tsx` instead, see the Schedule presets entry below.
- `POST/DELETE /api/admin/schedule/blocked/{id}` — one-off blocked dates/slots. Both times null = full day; otherwise both must be valid `HH:MM` with end after start (400, `BlockedTimesError`, also on the range endpoint) — a single missing time used to save as a full-day block
- `POST /api/admin/schedule/blocked/conflicts` (`{ startDate, endDate?, startTime?, endTime? }`) and `POST /api/admin/schedule/presets/conflicts` (`{ days, breaks, startDate?, endDate? }`; no `endDate` = permanent, from today, skipping dates a scheduled range covers) — preview the upcoming CONFIRMED appointments a block or schedule change would leave on a closed time (QA run 4: they stayed booked with no warning). `SchedulePage` (blocking) and `PresetEditorModal` (Apply, a date range, saving Default) list them via `components/admin/scheduleConflicts.ts` and, with the ticked-by-default checkbox, cancel them through the owner's normal cancel (customer notice included) after saving.
- `POST /api/admin/schedule/blocked/range` — blocks a consecutive streak of dates in one call (`startDate`/`endDate` inclusive, shared `startTime`/`endTime`/`reason`), inside one DB transaction so a failure partway rolls back the whole range; each date created is still an ordinary independent `BlockedSlot` row afterward, so the single-date endpoints above need no special-casing to edit/delete one. Kept alongside the single-date endpoint, not replacing it — `SchedulePage.tsx`'s Blocked Dates form has a "block a range" checkbox that reveals a second date input and switches which endpoint the same form submits to.
- **Schedule presets** — a named 7-day `WorkingHours` template (`SchedulePreset` + `SchedulePresetDay`), edited via `PresetEditorModal.tsx` (a "New Preset"/"Edit Preset" modal reusing the same `WeekHoursEditor` component the old editable Working Hours section used to, so designing a preset feels identical to editing a weekly template). Days are always caller-supplied — the modal opens pre-filled with a copy of the current live hours when creating, but the owner can freely redesign before saving. `SchedulePage.tsx` renders Working Hours and Saved Presets inside one merged card (one `<section>`, one heading pair) rather than two separate cards.
  - **Every business always has exactly one preset with `IsDefault = true`, named "Default"** — the baseline schedule. `SchedulePresetService.GetOrCreateDefaultPreset` lazily creates it (snapshotting current `WorkingHours`, or 09:00-18:00/inactive per missing day) if a business somehow doesn't have one; existing businesses got theirs backfilled by the `AddDefaultSchedulePreset` migration. In `PresetEditorModal.tsx`, editing the Default preset hides the name field (locked to "Default" server-side regardless of what's sent) and the entire "Use This Schedule" section (Apply Now / Schedule / Delete) — for Default, **Save IS apply**: `AdminController.UpdateSchedulePreset` pushes the edited days straight to live `WorkingHours` via `SchedulePresetService.ApplyPresetToWorkingHours` whenever no `PresetSchedule` is currently active (`SchedulePresetService.HasActiveSchedule`); if one is active, the edit is saved but takes effect only once that range reverts. `DeleteSchedulePreset` and `SchedulePresetForRange`/`ScheduleForRange` both reject the Default preset with 400 — it can't be deleted (the system always needs a baseline) and can't be scheduled for a date range (it already is the baseline).
  - `GET/POST /api/admin/schedule/presets`, `PUT .../presets/{id}` — list (Default sorted first, `.OrderByDescending(IsDefault)`; also where `GetOrCreateDefaultPreset` gets called so a fresh business immediately sees one), create (`SaveSchedulePresetRequest{Name,Days}`), rename/redesign an existing one (`UpdateSchedulePresetRequest`) — name is ignored for the Default preset, see above.
  - `DELETE /api/admin/schedule/presets/{id}` — 400 if `IsDefault`; otherwise blocked (400, not 500) while a `PresetSchedule` still references the preset as its target (`Restrict` FK, caught as `DbUpdateException`) — cancel that schedule first.
  - **Modal flow (redesigned 2026-09-23)**: one primary button whose action is picked by a radio group (Just save / Use it from now on / Only for specific dates). Apply and Schedule always **save the form first** (`persist()`), then call the endpoints below — they act on the server-side copy, so the old standalone Apply Now button silently ignored unsaved edits ("apply doesn't change anything"). Errors render in the sticky footer next to the button, not at the top of the scrolled body.
  - `POST .../presets/{id}/apply` — **immediate, permanent** ("Use it from now on"), via `SchedulePresetService.ApplyPresetPermanently`: applies the preset live **and copies its days + breaks into the Default preset** (changed 2026-09-23 — before, Default kept the old hours and silently came back on the next revert/Default save, making Apply look like it didn't stick). Also ends a currently *running* `PresetSchedule` (row deleted, no revert); a pending not-yet-started one is left alone and reverts to the new Default. No revert. (Hidden in the UI for the Default preset, where Save already does this — see above.)
  - `POST .../presets/{id}/schedule` (`SchedulePresetRangeRequest{StartDate,EndDate}`) — **temporary, self-reverting**: the template switches to this preset's days on `StartDate` and automatically reverts to the business's **Default preset** on the day after `EndDate` (`RevertToPresetId` is always the Default preset's id — there's no per-schedule backup snapshot anymore). Only one un-reverted `PresetSchedule` per business exists at a time — scheduling again **replaces** the existing one (changed 2026-09-23; it used to 400, which left no way to move a booked range's dates short of cancelling first). If the replaced range was already running and the new one starts in the future, live hours revert to Default in between. `PresetEditorModal` opens a preset that already has a range on its dates ("Save & update dates"), and warns when a range for a *different* preset will be replaced. Editing (PUT) a preset whose range is currently running also pushes the edit to live hours immediately. A range starting today or earlier applies immediately in the same request, rather than waiting for the next cron sweep. A range that has already ended is a 400 (it used to apply as if starting now). Rejected (400) if `id` is the Default preset.
  - `GET /api/admin/schedule/preset-schedule` — the business's current pending/active `PresetSchedule` if any (`{ schedule: PresetScheduleDto | null }`, always wrapped so the body is never a bare `null` — ASP.NET writes an *empty* body for a raw null `Ok(null)`, not literal `"null"`, which broke `GetFromJsonAsync`/`axios` parsing). `SchedulePage.tsx` shows this as a banner on the Working Hours section: "From X through Y, your schedule will be 'Name'" before it's applied, or "Your schedule is currently 'Name' until Y" once it is.
  - `DELETE /api/admin/schedule/preset-schedule/{id}` — "close"/cancel a pending or active scheduled change. Pending just deletes the row; active additionally reverts the template to the Default preset first.
  - `GET /api/cron/apply-scheduled-presets` (`CronController`, same `CronSecret` bearer pattern, `.github/workflows/cron-apply-scheduled-presets.yml`, daily) — `SchedulePresetService.ApplyDueScheduledPresets()`: applies any schedule whose `StartDate` has arrived, reverts (and deletes) any applied one whose `EndDate` has passed.
  - **Each preset also carries its own Recurring Breaks** (`SchedulePreset.Breaks` / `SchedulePresetBreak`, added 2026-09-21 via `AddSchedulePresetBreaks`) — unlike Days there's no fixed 7-row shape (zero or many breaks per day, same as the live `Break` table), so `AdminController.UpdateSchedulePreset` fully replaces the collection on every save (`db.SchedulePresetBreaks.RemoveRange` then re-add) rather than upserting in place. `SchedulePresetService.ApplyPresetToWorkingHours` applies both Days (→ `WorkingHours`) and Breaks (→ `Break`, via the new `SchedulePresetService.ReplaceBreaks`, a delete-then-insert) whenever a preset is applied — Apply Now, Schedule Range, or the Default preset's apply-on-save — so a preset's breaks travel with it the same way its hours do. `GetOrCreateDefaultPreset` snapshots current `Breaks` alongside `WorkingHours` when lazily creating the Default preset; existing Default presets (which predate this table) were backfilled by the migration. In `PresetEditorModal.tsx`, each day's breaks are edited inline under that day's row ("+ Add break" per day), with an optional "copy breaks from…" dropdown listing the business's other presets (client-side only — it copies already-fetched data into local form state, nothing persists until Save) — this is what backs the owner's request to make a new preset "the same" as another one's (e.g. the Default's) breaks without re-entering them by hand.
  - This area has gone through several redesigns in the same project — per-date "exception" overrides removed, a scheduled-range mechanism added, then a per-schedule auto-backup preset replaced by a single always-present Default preset with a read-only Working Hours view, then Recurring Breaks folded into the same per-preset model — see git history around `RemoveWorkingHoursOverride`, `AddPresetSchedule`, `AddDefaultSchedulePreset`, and `AddSchedulePresetBreaks` if extending this area again.

  (A per-date `WorkingHoursOverride` table/endpoint — first a standalone "Date-Specific Hours" section, then reframed as "Exceptions" inside Blocked Dates — was built and then fully removed after user feedback: reopening a date inside a blocked range is already just deleting that date's `BlockedSlot` row, which the Blocked Dates list already supports per-row. No separate override mechanism needed. If per-date hour customization is ever requested again, check git history for `RemoveWorkingHoursOverride` before rebuilding it from scratch.)
- `GET /api/admin/dashboard?week=0` — weekly appointments (week offset from current)
- `GET /api/admin/appointments?filter=today|upcoming|past` — appointment list (omit `filter` for all); `today`/`upcoming` sort soonest first, `past`/all newest first; each row includes `recurringSeriesId` (null for one-off bookings)
- `PATCH /api/admin/appointments/{id}` — cancel only (`{ status: "CANCELLED" }`); any other status is rejected — see [Appointment status](#appointment-status-no-manual-complete)
- `GET /api/admin/appointments/availability?date=&itemId=` — same slot computation as the public `GET /api/{slug}/availability`, but scoped by the JWT's `BusinessId` instead of a slug (keeps `AdminController` self-contained); backs both the New Appointment modal's slot grid and the recurring-series form's slot grid
- `GET /api/admin/customers/search?query=` — search this business's own `Customer` rows by name/phone (min 2 chars, top 20); backs `CustomerPicker`'s autocomplete
- `POST /api/admin/appointments` — owner books directly on a customer's behalf (existing `customerId` or new `customerName`+`customerPhone`, upserted by phone same as public booking); `MaxBookingsPerDay/Week` limits are **not** enforced here (they exist to stop customers gaming self-service booking, not to restrict the owner). `force: true` skips the working-hours/breaks/blocked-slot check (for walk-ins) but still hard-rejects an exact overlap with an existing appointment — see [Owner-created & recurring appointments](#owner-created--recurring-appointments)
- `GET /api/admin/recurring` — list this business's recurring series (active and inactive), each with its 5 most recent `RecurringSkip` entries and a computed `nextOccurrenceDate`
- `POST /api/admin/recurring` — create a weekly recurring series; immediately generates real `Appointment` rows for the rolling horizon (not just the next one) rather than waiting for the next cron run
- `DELETE /api/admin/recurring/{id}` — deletes the series **and cancels every not-yet-completed appointment it generated** (frees the slot for other bookings); already-completed appointments are left untouched as history

**Public booking (no JWT — `{slug}` identifies the tenant)**
- `GET /api/{slug}/info` — business name, items, active days (weekday template), `openDates` (the next 60 dates actually open per `GetEffectiveDay`, minus dates with a **full-day** `BlockedSlot` — what `BookingWizard`'s date picker filters on, so a scheduled preset range is honored and a closed day never appears; a partial block keeps the day listed), isRTL flag, plus `city`/`addressLine`/`mapUrl` and the rating aggregate (`ratingCount`, `ratingAverage`). Resolves by slug **regardless of `IsListed`** — unlisting only removes a business from the directory; a direct/shared link still works
- `GET /api/{slug}/availability?date=&itemId=` — available 30-min slots. For a reschedule, `&excludeAppointmentId=&token=` (its cancel token) leaves that appointment out, so it can move by less than its own length; the admin `appointments/availability` takes `excludeAppointmentId` alone, and every reschedule save excludes the row it moves
- `POST /api/{slug}/appointments/photo` — upload a reference photo for a `CustomerUpload`-mode item (anonymous); returns `{ url }` to pass as `customerPhotoUrl` below
- `POST /api/{slug}/appointments` — book appointment; **requires a customer session** (401 otherwise) and always books under the session's verified phone, ignoring `customerPhone` in the body; returns `{ appointmentId, cancelToken }`; auto-follows the business; if the item's `photoMode` is `OwnerGallery`/`CustomerUpload`, `galleryPhotoId`/`customerPhotoUrl` respectively is required
- `GET /api/{slug}/appointments/{id}?token=` — view appointment details (used by the public magic-link page); requires the cancelToken like cancel/reschedule (404 without it — ids are public via `availability/full`, and this response includes the customer phone + token)
- `DELETE /api/{slug}/appointments/{id}?token=` — cancel (validated by cancelToken) — routes through `AppointmentCancellationService.CancelFromCustomerAsync`, see [Waitlist & cancellation approval](#waitlist--cancellation-approval)
- `PATCH /api/{slug}/appointments/{id}?token=` — reschedule (re-checks availability first)

**Customer auth (no JWT)**
- `POST /api/customer/auth/whatsapp` — `{ token }`; redeems a `WhatsAppBookingToken` (issued by `WhatsAppController` once the customer picks an item in the chatbot) into a customer session — returns a customer JWT (`"type": "customer"` claim) plus `{ businessSlug, itemId }` so the frontend can land directly on date selection with the item preselected. 400 if the token is missing/expired, 404 if the business/item it points at is gone. See [Customer login via WhatsApp](#customer-login-via-whatsapp).
- `POST /api/customer/auth/otp` — `{ phone }`; sends a 6-digit SMS code (`devOtp` in the response body in Development), 45s cooldown + 5/hour cap; returns `{ isNewCustomer }`. `POST /api/customer/auth/verify` — `{ phone, otp, name?, familyName? }`; verifies the code and returns the same customer-JWT shape as the WhatsApp login (`name`/`familyName` required only for a brand-new account). A second, parallel entry point alongside WhatsApp login — see [Customer login via phone+OTP](#customer-login-via-phoneotp).

**Business directory / discovery (no JWT except follow)**
- `GET /api/businesses/search?query=&businessTypeKey=&city=&sort=&page=&pageSize=` — public directory. Base filter `IsListed` + `BookingRules.AcceptsBookingsQuery` (not disabled, not expired, trial not over once billing exists). `sort`: `rating` (default — avg desc, then count, then name), `popular` (follower count), `newest`, `name`. Returns `PagedResult<BusinessSearchResultDto>` (`{ items, page, pageSize, total, hasMore }`); each item carries `businessTypeKey`, `city`, `ratingAverage`, `ratingCount`, `followerCount`, `isFollowed`. `query`/`city` match case-insensitively via `lower()` (not `EF.Functions.ILike`, which the SQLite test provider can't run)
- `GET /api/businesses/cities` — distinct trimmed cities among listed businesses that take bookings (backs the browse city filter)
- `GET /api/businesses/{slug}/reviews?page=&pageSize=` — public, non-hidden reviews newest-first as `PublicReviewListDto` (rating aggregate + `PagedResult<PublicReviewDto>`); reviewer shown as "First L."
- `GET /api/businesses/followed`, `POST/DELETE /api/businesses/{slug}/follow` — manage followed businesses (customer JWT, `CustomerOnly`)
- `GET /api/business-types` (`BusinessOwnerRequestsController`) — active `BusinessTypeDefinition` rows, ordered by display name; backs both the public request form's picker and the browse category chips

**Business owner onboarding (no JWT except the review side)**
- `POST /api/business-owner-requests/send-email-code` — public `{ email }`; sends a 6-digit code via the admin's Gmail (`IOwnerEmailSender`); rate-limited (45s cooldown, 5/hour)
- `POST /api/business-owner-requests` — public submission `{ businessName, ownerFirstName, ownerFamilyName, email, phone, businessTypeId, businessDescription?, systemNeeds?, code }`; `code` must match an unconsumed, unexpired row from `send-email-code` for that email (400 otherwise); names must be English-letters-only (the username is derived from them); phone must be 7–15 digits; 400 on an email that already has a `Business`, 409 on a second concurrent `Pending` request for the same email; best-effort admin-notification email
- Platform-admin review side is under `/api/platform-admin` — see [Platform admin](#platform-admin) below

**Reviews (customer JWT, `CustomerOnly`)**
- `GET /api/reviews/eligibility?businessSlug=` — `{ canReview, alreadyReviewed, review? }`. `canReview` needs a **completed** appointment (Status `CONFIRMED` + effective end time past, per `AppointmentStatusHelper`; no stored `COMPLETED`) and `!PendingCancellationApproval`
- `POST /api/reviews` — `{ businessSlug, rating (1–5), comment? }`. **403** without a completed appointment, **409** if a review already exists (frontend PATCHes instead). Stamps `AppointmentId` from the most-recent completed visit; recomputes the business aggregate
- `PATCH/DELETE /api/reviews/{id}` — author-scoped (`r.CustomerAccountId == accountId`, else 404); both recompute the aggregate

**Waitlist (customer JWT, `CustomerOnly`)**
- `POST /api/{slug}/waitlist/{appointmentId}?date=&startTime=` — join the waitlist for a currently-CONFIRMED appointment; 400 if the business hasn't turned `WaitlistEnabled` on; idempotent (a repeat join for the same customer+appointment is a no-op 200, not a duplicate row). `date`/`startTime` are the slot the page showed (optional, `BookingWizard` sends them): if the appointment has moved since, 409 `{ slotChanged: true }` and the wizard reloads the times (QA run 4: the join followed the moved appointment)

**Customer account (customer JWT required, `CustomerOnly` policy)**
- `GET /api/customer/appointments?filter=` — this customer's appointment history across all businesses (rows whose `Customer.CustomerAccountId` is this account); `upcoming`/`today` soonest first, others newest first
- `POST /api/customer/appointments/{id}/cancel`, `PATCH /api/customer/appointments/{id}/reschedule`, `PATCH /api/customer/appointments/{id}/notes`
- `PATCH /api/customer/appointments/{id}/photo` — change a CONFIRMED appointment's reference photo (only for items with `photoMode != None`); same `galleryPhotoId`/`customerPhotoUrl` shape as booking

**Platform admin (`PlatformAdminOnly` except bootstrap/login)**
- `GET /api/platform-admin/bootstrap-available` — `{ available }`, true until the first admin account exists
- `POST /api/platform-admin/bootstrap` — creates the (single, for now) platform admin account; 403 once one already exists, so it's safe to leave the endpoint public
- `POST /api/platform-admin/login` — email+password, returns a platform-admin JWT (`"type": "platform_admin"` claim, separate from Business/CustomerAccount tokens)
- `GET /api/platform-admin/businesses?search=&page=&pageSize=`, `GET .../businesses/{id}` — search/detail across every tenant. This list and `GET .../customers?search=&page=&pageSize=` match case-insensitively and return `PagedResult` (default 50, max 100 a page); customer search also matches a local phone (050…) against the stored E.164
- `PUT /api/platform-admin/businesses/{id}/paid-until` `{ paidUntil: "yyyy-MM-dd" | null }`, `GET /api/platform-admin/paid-period-ended` — manual payment tracking, see Paid period in the platform-admin skill
- `POST /api/platform-admin/businesses/{id}/whatsapp/link`, `GET .../whatsapp/status`, `DELETE .../whatsapp/link` — link/poll/unlink a business's self-hosted WhatsApp chatbot session (see [WhatsApp chatbot: self-hosted via Baileys](#whatsapp-chatbot-self-hosted-via-baileys-whatsapp-bridge))
- `GET /api/platform-admin/businesses/{id}/activity`, `GET .../customers/{id}/activity` — that entity's `ActivityLog` rows, newest first. `impersonated` = done with an impersonation token; `byPlatformAdmin` = the admin's own action (`PlatformAdminController.*`/`WhatsAppLink.*` rows, which also store the admin id in `ImpersonatedByPlatformAdminId`)
- `POST /api/platform-admin/businesses/{id}/impersonate`, `POST .../customers/{id}/impersonate` — mint a real Business/Customer JWT on their behalf for support purposes; every action taken with it is logged with `ImpersonatedByPlatformAdminId` set
- `GET /api/platform-admin/business-owner-requests?status=`, `GET .../{id}` — review queue for [Business owner onboarding](#business-owner-onboarding-self-service--admin-approved) requests
- `POST /api/platform-admin/business-owner-requests/{id}/approve` — `{ slug }`; creates the `Business` (system-generated `Username`, random temp password, `MustChangePassword = true`, `EmailVerified = true` since the admin already vetted it), emails the credentials best-effort through the owner Gmail sender (`IOwnerEmailSender`, like the platform-admin reset-password email, 2026-10-20), and **always returns the temp password in the response** so the admin can hand it over manually if the email failed
- `POST /api/platform-admin/business-owner-requests/{id}/reject` — `{ note? }`; conditional on still `Pending` (409 otherwise, also when it was already reviewed, and for a racing approve); writes an `ActivityLog` row with no `BusinessId` and emails the requester via Gmail (`NotificationOutbox.AddOwnerEmail`) **without** the note, which stays internal
- `GET /api/platform-admin/reviews?businessId=`, `POST .../reviews/{id}/hide|unhide` — moderation (toggles `Review.IsHidden`, recomputes the business's rating aggregate)

**Integrations**
- `POST /api/whatsapp/bridge/inbound` — active inbound path; called by the self-hosted whatsapp-bridge service (auth: `X-Bridge-Secret`), resolves the business directly by `BusinessId`, drives the item-selection chatbot flow (see below) plus cancel/reschedule keywords, in the business's language
- `POST /api/whatsapp/bridge/outgoing` — the bridge reports a message the owner typed on the linked phone (`X-Bridge-Secret`), see [Owner Chats page](#owner-chats-page)
- `POST /api/whatsapp/bridge/session-event` — the bridge reports a WhatsApp-side logout; emails the platform admin (see the logout alert under [WhatsApp chatbot](#whatsapp-chatbot-self-hosted-via-baileys-whatsapp-bridge))
- `POST /api/whatsapp/webhook` — dormant legacy Twilio webhook (validates X-Twilio-Signature); kept as a fallback path, see [WhatsApp chatbot: self-hosted via Baileys](#whatsapp-chatbot-self-hosted-via-baileys-whatsapp-bridge)
- `GET /api/cron/reminders` — sends two kinds of WhatsApp reminders in one call: a day-before one (`a.Date == tomorrow`, `ReminderSent` flag) and a ~3-hours-before one (local start within the next 3 hours, `ReminderSentSoon` flag), each idempotent via its own flag so repeated calls are safe; requires `Authorization: Bearer <CronSecret>`; response shape `{ dayBefore: { total, sent, failed }, soon: { total, sent, failed } }`; triggered every 15 minutes by an external cron-job.org job, not GitHub Actions — see the cron scheduling note below
- `GET /api/cron/generate-recurring` — extends every active `RecurringSeries`' generated `Appointment` rows to the rolling horizon (default 8 weeks, `RecurringGeneration:HorizonWeeks` config); same `Authorization: Bearer <CronSecret>` gate, response shape `{ total, created, skipped }`; triggered once daily by `.github/workflows/cron-generate-recurring.yml` — see [Owner-created & recurring appointments](#owner-created--recurring-appointments)
- `GET /api/cron/apply-scheduled-presets` — `SchedulePresetService.ApplyDueScheduledPresets()`: applies any `PresetSchedule` whose `StartDate` has arrived and reverts (then deletes) any applied one whose `EndDate` has passed; same `Authorization: Bearer <CronSecret>` gate, response shape `{ applied, reverted }`; triggered once daily by `.github/workflows/cron-apply-scheduled-presets.yml` — see the Schedule presets entry above
- `GET /api/cron/charge-subscriptions` — charges every `ACTIVE` business with a stored `CardcomToken` whose `CardcomNextChargeAt` has passed, via Cardcom's token-charge API; same `Authorization: Bearer <CronSecret>` gate, response shape `{ total, charged, failed }`; a successful charge bumps `CardcomNextChargeAt` by 1 month, a failed one sets `SubscriptionStatus = EXPIRED`; triggered once daily by `.github/workflows/cron-charge-subscriptions.yml` — see [Billing (Cardcom)](#billing-cardcom)
- `GET /api/cron/retry-waitlist-notifications` — calls `WaitlistService.AdvanceQueues` (same as the in-process `WaitlistQueueWorker`, kept as a backstop): for every cancelled appointment with still-`WAITING` entries, messages the next one in line if nobody was reached yet or the last message is at least 5 minutes old; same `Authorization: Bearer <CronSecret>` gate, response shape `{ total, sent, failed }`; triggered every 15 minutes by an external cron-job.org job, not GitHub Actions — see the cron scheduling note below

**Cron scheduling**: `generate-recurring` and `charge-subscriptions` only need to run once a day, so
`.github/workflows/cron-generate-recurring.yml`/`cron-charge-subscriptions.yml` (GitHub Actions
`schedule` trigger) are reliable enough for them. `reminders` and `retry-waitlist-notifications`
need a genuine ~15-minute cadence, and GitHub Actions does **not** reliably honor sub-hourly
`schedule` triggers (confirmed in practice: a `*/15 * * * *` workflow on this repo actually fired
every 2-4 hours) — those two are instead triggered by external cron-job.org jobs calling the same
endpoints with the same `Authorization: Bearer <CronSecret>` header, configured directly on
cron-job.org's dashboard (not tracked in this repo).
